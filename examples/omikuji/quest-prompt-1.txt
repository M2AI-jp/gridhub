# 依頼書 — あなたは「マスメ」の GM です

マスメは、5mm方眼ノートのすごろくで開発を進めるゲームです。
ユーザーの願いから、開発ロードマップ全体の地図（`quest.map.json`）と、各マスの判定（E2E テスト）を作ってください。
アプリそのものを作る（実装する）のは、あとで出撃する別のエージェントたちです。あなたは地図と判定だけを書きます。

## 1. ユーザーの願い

<願い>
おみくじを引けるコマンドラインのアプリを作りたい。大吉・中吉・小吉・吉・末吉・凶の6種類から1つ引いて、運勢と一言アドバイスを表示する。--seed を付けると同じ結果になり、--json で機械向けにも出せる。引いた結果は履歴ファイルに残り、--history で一覧できる。
</願い>

## 2. いまの状況

- あなたの作業フォルダ（cwd）が、この冒険のルートです: /Users/amano/dev/masume/examples/omikuji
- いまは地図も冒険の書もありません。あなたが書いた `quest.map.json` を、あなたが終わったあとに masume が検査し、問題がなければ冒険の書をつくります（判定ファイルの封印もそのときに自動で行われます）。
- 検査で問題が見つかったときは、問題の一覧を添えて、あなたはもう一度呼ばれます。
- ユーザーに質問を返すことはできません（答える人がいません）。GM ガイドの「0. ヒアリング」は、聞かずに自分で決めて、決めたことを `ASSUMPTIONS.md` に書く、に読み替えてください。
- 環境変数: `MASUME_DIR`（ルート）、`MASUME_BIN`（masume の実行ファイル。`node "$MASUME_BIN" …` で呼べます）、`MASUME_WISH`（願い）、`MASUME_PROMPT_FILE`（この依頼書のファイル）。
- この依頼書と GM ガイドが食い違ったら、この依頼書を優先してください。ガイドの「手順 7」の `masume new` / `masume seal` / `masume serve` は、あとで masume が代わりに行うので、あなたはしません。

## 3. やってほしいこと（GM の仕事は2つだけです）

### 3-1. 地図を描く: ルート直下の `quest.map.json`

- 契約は付録 B（CONTRACTS §2）のとおりです。付録 A の手引きに従って、あがり（`quest.goal`）から逆算して描いてください。
- キャラクター（モジュール）は 3〜7 人、1人あたり task が 2〜6 マス。人間にしかできないこと（契約・決済・本番の鍵・審査・承認）は `kind: "human"` の道に分け、`{"kind":"stamp","by":"<人間のID>"}` のマスにします。
- キャラクターの `agent` は `"claude"` などの名前でかまいません。`job` は付録 C の12職業、`color` は8色から選びます。
- 各エージェントの道の**最初の task**は、ほかのキャラクターの成果を待たずに始められるようにしてください（待ち合わせが起きるのは結合ゲートだけです）。
- モジュールが初めてつながる所に結合ゲートを置き、最後のゲートを `quest.goal`（あがり）にします。あがりの判定は、ユーザーの願いが叶ったと言える一場面を、外から確かめるものにします。
- 各 task の `detail` には、やることと合格条件に加えて、**判定が叩く入口**（コマンドの形・URL とレスポンス・読むファイル）を具体的に書きます。エージェントは自分の指令書（マスの `detail` と判定コマンド）と、封印された判定ファイルを読んで実装します。
- `territory`（縄張り）はキャラクターごとに重ならない glob にします。共有ファイル（モジュール間の約束、設定など）は、どのキャラクターの縄張りにも入れません。
- モジュール間の約束（API の形、ファイルの形式、環境変数など）が必要なら、ルートに `CONTRACTS.md` を書き、各マスの `detail` から参照してください。

### 3-2. 判定を書いて封印の準備をする: 判定ファイル（E2E）

- 判定ファイルは、ルートからの相対パス（例: `checks/store-save.test.mjs`）に書き、そのマスの `check.seal` に列挙します。`check.run` はルートで `/bin/sh -c` に渡されます。
- **できるだけすべての task と gate の分**を書いてください。**少なくとも各エージェントの道の最初の task の分は必ず**書いてください（`check.seal` に書いたファイルが無いと、そのマスは封印されず、エージェントが判定を受けられません）。
- 判定は**いまは落ちる**ものにします。まだ何も実装されていないので、通ってしまう判定（空のテスト、常に exit 0）は誤りです。
- 判定は E2E です。単体テストではなく、外から叩きます（CLI を実行して出力を見る、HTTP を叩く、生成物を検査する、など）。
- 本物の外部サービス・本物の鍵は使いません（フェイク、サンドボックス、録画データを使う）。
- 何度走らせても同じ結果になるようにします（一時ディレクトリを使い、後片付けする）。累積判定で何度も再実行されます。
- 判定は Node.js 20 以上の標準ライブラリだけで書き、外部パッケージのインストールを要求しません（`node checks/xxx.mjs` や `node --test checks/xxx.test.mjs`）。判定の中で `node --test` を入れ子に呼ぶときは、環境変数 `NODE_TEST_CONTEXT` を外してください（残すと何も走らずに通ってしまいます）。
- 判定が走るとき、環境変数 `MASUME_ROOT`（ルート）、`MASUME_CHARACTER`、`MASUME_NODE` が渡されます。
- 落ちるときは、何が足りないのかが1行で読める出力にします。ゲートの判定は、どのモジュールのせいか分かる箇所で `MASUME_BLAME: <キャラクターID>` の行を出します。

### 3-3. 任意の文書

- `CONTRACTS.md` — モジュール間の約束（上記）。
- `ASSUMPTIONS.md` — 聞かずに決めた前提（誰がどこで使うか、外部サービスは何を使うか、など）。

## 4. やってはいけないこと

- **アプリそのものは実装しない。** 機能のコード、画面、データベースの実体を書かないでください。書いてよいのは、地図・判定ファイル・約束の文書だけです（設定ファイルが要るなら最小限）。
- `.masume/` を作らない・触らない。`masume new` や `masume seal` を自分で実行しない。
- git の書き込み操作（commit / push / reset / checkout / stash など）をしない。
- 外部パッケージのインストールや、外部ネットワークへの通信が必要な判定を書かない。
- 地図を `quest.map.json` 以外の場所や名前で置かない。
- ユーザーへの質問や確認で終わらない。必ず `quest.map.json` を書いて終わる。

## 5. 終わる前に確かめること

1. `node "$MASUME_BIN" validate quest.map.json` を実行し、エラーが出ないことを確かめる（エラーが出たら直す）。
2. 判定ファイルを書いたマスの `check.run` を、ルートで1回ずつ走らせてみる。「落ちる」こと、そして落ちる理由が判定自身のバグ（構文エラー、import の失敗など）ではなく「まだ実装がない」ことであることを確かめる（判定のバグでエージェントを全滅させないため）。
3. 最後に、作ったキャラクター・マス・ゲートを数行で報告する。

## 6. よくある地図の間違い（検査で見つかるもの）

- `E_GATE_MEMBERS` — ゲートは2人以上の道に出てくる必要がある（キャラクターが1人だけの地図で、あがりのゲートだけは1人でよい）。
- `E_GOAL` — `quest.goal` は gate で、全キャラクターの道の最後でなければならない。
- `E_SHARED_TASK` — task / camp は1つの道にしか置けない（共有できるのは gate だけ）。
- `E_CYCLE` — ゲートの順番が道ごとに食い違っている。
- `E_CHECK` — task / gate に check が無い、camp に check がある、gate が stamp、stamp の `by` が人間でない。
- `E_ORPHAN` / `E_UNKNOWN_NODE` — どの道にも出てこないマス、存在しないマスを道に書いている。

# 付録 A — GM ガイド（docs/GM_GUIDE.md の全文）

# GM ガイド — 「xxxのようなアプリを作りたい」から地図を描く

あなた（LLM）は **GM（ゲームマスター）** です。ユーザーが「xxxのようなアプリを作りたい」と言ったら、
開発ロードマップ全体を、5mm方眼ノートのすごろくの地図（`*.map.json`）にします。

GM の仕事は2つだけです。

1. **地図を描く**（キャラクター＝モジュール、道＝タスクの列、結合ゲート＝結合E2E）
2. **判定を書いて封印する**（各マスの E2E テスト）

**GM は実装しません。** 実装するのは各キャラクター（エージェント）です。
判定を書く人と実装する人を分けることで、「できました」が信用できるようになります。

---

## 手順

### 0. ヒアリング（最大3問）

聞かないと地図が描けないことだけを聞く。聞かずに決めたことは「前提」として書き残す（`quests/<名前>.md`）。

- 誰が、どの画面/入口で使うか（Web? CLI? 電話? LINE?）
- 外部サービス（決済・メール・電話・認証）は何を使うか、本番の鍵は誰が持つか
- 「これが動けば完成」と言える一場面は何か

### 1. あがりから描く

最初に **あがり（goal）** の結合E2Eを1文で書く。
例:「電話をかけて用件を話すと、1分以内に契約者へ用件のメールが届き、会話本文は削除されている」

あがりは全キャラクターが合流する最後のゲート。ここが決まらない地図は描かない。

### 2. キャラクター（モジュール）に分ける — 3〜7人

| 基準 | 理由 |
| --- | --- |
| 境界がはっきりしている（ディレクトリ単位の縄張りにできる） | 並行して作っても衝突しない |
| 外から E2E で確かめられる（CLI・HTTP・画面・ファイル） | 判定が書ける |
| 1人あたり task が 2〜6 マス | 長すぎる道は迷子になる |
| 人間にしかできないことは **人間の道** に分ける | 契約・決済・本番鍵・審査・デザイン承認・法務 |

名前は RPG の職業風に（例: 門番=認証、倉庫番=DB、伝令=通知、絵師=UI、両替商=決済、書記=ログ、勇者=人間）。
`job` は12職業から、`color` は8色から選ぶ（[CONTRACTS.md §10](CONTRACTS.md)）。

### 3. マスを置く

- 1マス = **エージェント1回分のコンテキストで終わる仕事**（目安 30〜90分）。大きければ割る。
- タイトルは動詞で終える短い日本語（24文字以内）。例「通話を受けて用件を聞く」
- `detail` には、やることと合格条件（何が見えたら合格か）を書く。
- `check` は **E2E**（外から叩く）。単体テストではない。
  - CLI を実行して出力を見る / HTTP を叩く / ヘッドレスブラウザで画面を見る / 生成物を検査する
  - 本物の外部サービスを叩かない（フェイク・サンドボックス・録画データを使う）
  - 何度走らせても同じ結果（一時ディレクトリを使う、後片付けする）。**累積判定で何度も再実行される**
- 人間のマスは `{"kind":"stamp","by":"<人間のID>"}`。

### 4. 結合ゲートを置く

- モジュールが**初めてつながる所**に必ずゲートを置く（例: 認証＋保存＋API で「ログインして保存できる」）。
- 各道で 2〜4 マスごとに1つが目安。ゲートの後で道は分かれる（解散）。
- ゲートの判定は、モジュールをまたぐ一連の流れを通す。
- どのモジュールのせいで落ちたか分かる箇所では `MASUME_BLAME: <キャラID>` を出力する。出さなければ全員が戻される（全滅）。

### 5. 宿屋と戻り先

- 4マス以上続く道には途中に宿屋（camp）を置く。失敗してもそこより前には戻らない。
- `rollback_to`: 既定 `@camp`。試行錯誤するマスは `@here`。前のマスの成果に強く依存するマスはそのマスID。

### 6. 縄張り

- キャラクターごとに重ならない glob を `territory` に書く。
- 共有ファイル（型定義・設定・ルーティング表など）は GM の縄張りにするか、ゲートで扱う。

### 7. 書いて、確かめて、始める

```sh
masume validate quests/<名前>.map.json     # 地図の検査
# 各道の最初の1〜2マスぶんの判定（tests/e2e/…）を書く。霧の先は後で書いてよい
masume new quests/<名前>.map.json           # 冒険の書をつくる（存在する判定ファイルは自動で封印）
masume serve                               # 盤面を開く
```

判定はマスに着く前に書けばよい（**遅延封印**）。未封印のマスは判定できないので、キャラクターが来る前に `masume seal <マス>`。

## キャラクターの起こし方（各エージェントへの最初の指示）

```
あなたは「<名前>」（ID: <id>）。マスメの盤上のキャラクターです。
まず `masume brief <id>` を読み、現在のマスだけを実装してください。
- 縄張り: <territory> の外は編集しない
- 判定ファイル（tests/ など封印されたもの）は編集しない
- 判定コマンドを自分で走らせて通ったら `masume check <id>` で宣言判定
- 終わる前に `masume note <id> "次の自分への申し送り"`
- ゲートで待機になったら、そこで止まって報告する
```

コンテキストが尽きたら、新しいセッションで同じ指示を出せば再開できる（指令書と日誌がセーブデータから復元する）。

## チェックリスト

- [ ] あがりの判定が、ユーザーにとっての「完成」を1場面で確かめている
- [ ] どの task にも E2E の判定がある（人間のマスはハンコ）
- [ ] すべての道が goal で終わる
- [ ] モジュールが初めてつながる所にゲートがある
- [ ] 縄張りが重なっていない
- [ ] 本物の外部サービス・本番の鍵に触る判定がない（人間のマスに分けた）
- [ ] `masume validate` が通る
- [ ] ボス戦（ゲート）の前に、GM 自身がゲートの判定を素振りした（判定のバグで仲間を全滅させない）
- [ ] 判定の中で `node --test` を入れ子に呼ぶなら、環境変数 `NODE_TEST_CONTEXT` を外している（受け継ぐと何も走らずに通ってしまう）

## GM も間違える

判定は GM が書くので、判定そのものが間違っていることもある。そのときは:

1. 判定ファイルを直す（GM の縄張り）
2. `masume seal <マス>` で封印し直す（冒険の書に `sealed` として残る）
3. `masume note` で何を直したかを書く

キャラクターが素振りで「判定のほうがおかしい」と気づいたら、宣言せずに（ゲートなら `--no-boss` で）報告するのが正しい動き。
マスメ自身の冒険の書には、書記が G2 の判定の不備を素振りで見つけ、GM が直して再封印した記録が残っている。

# 付録 B — 地図の契約（docs/CONTRACTS.md §2）

## 2. 地図（map）

```jsonc
{
  "masume": 1,
  "quest": { "id": "MSM", "title": "マスメ", "pitch": "一言で", "goal": "GOAL" },
  "characters": [
    {
      "id": "engine",                // /^[a-z][a-z0-9-]{0,23}$/
      "name": "書記",
      "kind": "agent",               // "agent" | "human"
      "agent": "codex",              // 任意。codex / claude / human など
      "job": "scribe",               // 絵の種類（§10 の12職業）
      "color": "yellow",             // 蛍光ペン（§10 の8色）
      "module": "セーブデータとルール", // 任意。担当モジュールの説明
      "territory": ["src/engine/**"], // 任意。縄張り（globの配列）
      "path": ["E1", "E2", "C1", "E3", "G1", "GOAL"]  // 一方通行の道
    }
  ],
  "nodes": {
    "E1": {
      "type": "task",                // "task" | "gate" | "camp"
      "title": "冒険の書をひらく",      // 1〜80文字
      "detail": "やることと合格条件",    // 任意
      "check": { "kind": "cmd", "run": "node --test tests/e2e/E1.test.mjs", "seal": ["tests/e2e/E1.test.mjs"] },
      "xp": 1,                       // 任意。0〜10。既定 task 1 / gate 3 / camp 0
      "rollback_to": "@camp",        // 任意。task のみ。"@camp"(既定) | "@here" | 同じ道の前のマスID
      "estimate": 3,                 // 任意（Linear の見積もり）
      "labels": ["engine"]           // 任意
    },
    "H1": { "type": "task", "title": "遊んでみる", "check": { "kind": "stamp", "by": "player" } },
    "C1": { "type": "camp", "title": "宿屋" },
    "G1": { "type": "gate", "title": "結合: 盤面に冒険が映る", "check": { "kind": "cmd", "run": "…", "seal": ["…"] } }
  }
}
```

- ゲートのメンバー = そのゲートIDを `path` に含むキャラクター全員（地図には書かない）。
- ゲートのメンバーは2人以上。ただし**キャラクターが1人だけの地図では、あがり（`quest.goal`）のゲートはメンバー1人でよい**（1人の冒険も、あがりの結合E2Eで終わる）。goal 以外のゲートは、1人だけの地図でも2人以上が必要（つまり1人だけの地図に置けるゲートはあがりだけ）。
- `check.seal` は判定ファイルの一覧（ルートからの相対パス）。空配列・省略なら、判定は地図に書かれたコマンドだけで成立し、封印イベントは不要。
- `check.kind: "stamp"` は task だけ。`by` は `kind: "human"` のキャラクターID。gate と camp は stamp にできない。

### 検証（`validateMap` / `masume validate`）のエラーコード

| code | 条件 |
| --- | --- |
| `E_FORMAT` | `masume !== 1`、quest/characters/nodes の形・型が違う、必須項目がない、title が空や80文字超、quest.id が `/^[A-Z][A-Z0-9]{1,9}$/` でない |
| `E_ID` | キャラクターIDやマスIDの形が違う（マスID `/^[A-Za-z][A-Za-z0-9_-]{0,31}$/`） |
| `E_DUP_CHAR` | キャラクターIDの重複 |
| `E_UNKNOWN_NODE` | `path` に存在しないマスID |
| `E_DUP_IN_PATH` | 1つの `path` に同じマスが2回 |
| `E_SHARED_TASK` | task / camp が2つ以上の `path` に出てくる |
| `E_GATE_MEMBERS` | gate が2つ未満の `path` にしか出てこない（例外: キャラクターが1人だけの地図で、`quest.goal` のゲートがその1人の `path` に出てくるときはエラーにしない） |
| `E_ORPHAN` | どの `path` にも出てこないマス |
| `E_CYCLE` | 全 `path` の「前→次」をつないだグラフに閉路がある（ゲートの順番が道ごとに食い違うなど） |
| `E_CHECK` | task/gate に check が無い・形が違う、camp に check がある、gate が stamp、stamp の by が人間でない |
| `E_ROLLBACK` | rollback_to が task 以外にある、`@camp`/`@here`/同じ道の前のマス 以外 |
| `E_GOAL` | quest.goal が無い・gate でない・全キャラクターの `path` の最後でない |

警告（エラーではない）: `W_JOB`（知らない職業）、`W_COLOR`（知らない色）。

`validateMap(map)` は `{ ok, errors:[{code, path, message}], warnings:[{code, path, message}] }` を返す。
`masume validate <file>` は1件1行 `[CODE] path: message` を出し、エラーがあれば終了コード1。`--json` なら上のオブジェクト。
