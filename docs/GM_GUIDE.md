# GM ガイド — 「xxxのようなアプリを作りたい」から地図を描く（GridHub）

あなた（LLM）は **GM（ゲームマスター）** です。ユーザーが「xxxのようなアプリを作りたい」と言ったら、
開発ロードマップ全体を、5mm方眼ノートのすごろく（JRPG）の地図（`*.map.json`）にします。
**意味のないマスはない**: 普通のマスはテスト1件、ダンジョンはタスク、町は Git のセーブ、中ボスは結合テスト、魔王はあがり、王様の城は人間のハンコ（[GAME_DESIGN.md](GAME_DESIGN.md)）。

GM の仕事は2つだけです。

1. **地図を描く**（キャラクター＝モジュール、道＝タスクの列、結合ゲート＝結合E2E）
2. **判定を書いて封印する**（各マスの E2E テスト）

**GM は実装しません。** 実装するのは各キャラクター（エージェント）です。
判定を書く人と実装する人を分けることで、「できました」が信用できるようになります。

## 手順

### 0. ヒアリング（最大3問）

聞かないと地図が描けないことだけを聞く。聞かずに決めたことは「前提」として書き残す（`quests/<名前>.md`）。

- 誰が、どの画面/入口で使うか（Web? CLI? 電話? LINE?）
- 外部サービス（決済・メール・電話・認証）は何を使うか、本番の鍵は誰が持つか
- 「これが動けば完成」と言える一場面は何か

### 1. あがりから描く

最初に **あがり（goal）** の結合E2Eを1文で書く。
例:「電話をかけて用件を話すと、1分以内に契約者へ用件のメールが届き、会話本文は削除されている」

あがりは全キャラクターが合流する最後のゲート。ここが決まらない地図は描かない。

### 2. キャラクター（モジュール）に分ける — 3〜7人

| 基準 | 理由 |
| --- | --- |
| 境界がはっきりしている（ディレクトリ単位の縄張りにできる） | 並行して作っても衝突しない |
| 外から E2E で確かめられる（CLI・HTTP・画面・ファイル） | 判定が書ける |
| 1人あたり task が 2〜6 マス | 長すぎる道は迷子になる |
| 人間にしかできないことは **人間の道** に分ける | 契約・決済・本番鍵・審査・デザイン承認・法務 |

名前は RPG の職業風に（例: 門番=認証、倉庫番=DB、伝令=通知、絵師=UI、両替商=決済、書記=ログ、勇者=人間）。
`job` は12職業から、`color` は8色から選ぶ（[CONTRACTS.md §10](CONTRACTS.md)）。

### 3. ダンジョン（task）とマス（テスト）を置く

- ダンジョン1つ = **エージェント1回分のコンテキストで終わる仕事**（目安 30〜90分）。大きければ割る。
- **マス1つ = テスト1件 = 1つの変数（値・状態・分岐）に対する小さな作業**。`check.cases` にテストの名前を並べ、判定ファイルの中のテストの名前をそれと同じにする（`node --test` の `test('<名前>', …)`）。名前は、変える値と期待を技術の言葉で（例「`title` が空なら 400 を返す」）。
- **ダンジョンは 2〜6 マス**。7マス以上なら2つに割る。
- タイトルは技術の言葉を先に、動詞で終える短い日本語（24文字以内）。例「`POST /api/memos` でメモを保存する」
- `detail` には、やることと合格条件（何が見えたら合格か）を書く。
- `check` は **E2E**（外から叩く）。単体テストではない。
  - CLI を実行して出力を見る / HTTP を叩く / ヘッドレスブラウザで画面を見る / 生成物を検査する
  - 本物の外部サービスを叩かない（フェイク・サンドボックス・録画データを使う）
  - 何度走らせても同じ結果（一時ディレクトリを使う、後片付けする）。**累積判定で何度も再実行される**
- 人間のマスは `{"kind":"stamp","by":"<人間のID>"}`。

### 4. 結合ゲートを置く

- モジュールが**初めてつながる所**に必ずゲートを置く（例: 認証＋保存＋API で「ログインして保存できる」）。
- 各道で 2〜4 マスごとに1つが目安。ゲートの後で道は分かれる（解散）。
- ゲートの判定は、モジュールをまたぐ一連の流れを通す。
- どのモジュールのせいで落ちたか分かる箇所では `MASUME_BLAME: <キャラID>` を出力する。出さなければ全員が戻される（全滅）。

### 5. 町（セーブ）と戻り先

- 町（camp）= セーブ。`quest.save: "git"` の冒険では、町に着くとそのキャラクターの縄張りがコミットされ、負けたらそのコミットに戻る（`gridhub quest` で生まれる冒険は既定で `"git"`）。
- 町は 2〜3 ダンジョンごとと、中ボスの直前に置く。失敗してもそこより前には戻らない。
- `rollback_to`: 既定 `@camp`。試行錯誤するマスは `@here`。前のマスの成果に強く依存するマスはそのマスID。

### 6. 縄張り

- キャラクターごとに重ならない glob を `territory` に書く。
- 共有ファイル（型定義・設定・ルーティング表など）は GM の縄張りにするか、ゲートで扱う。

### 7. レベルデザイン（地図の決まり）

名作 JRPG の作り方（[GAME_DESIGN.md](GAME_DESIGN.md) §1・§6）から。

- **ゴールから描く。** 先に魔王の城（あがりの結合 E2E）を1文で書く。盤面の1ページ目から見えるので、始まりから目的が分かる。
- **1マス = 1つの変数に対する小さな作業 + テスト1件。** ダンジョンは 2〜6 マス。
- **最初の地方はやさしく。** 最初のダンジョンは 1〜2 マス、最初の町は早めに。ここでルールが全部分かるようにする。
- **緊張と安心を交互に。** 町は 2〜3 ダンジョンごとと、中ボスの直前に置く。町の遠い地方は、意図して置く難所。
- **中ボスは、モジュールが初めてつながる所。** 地方の長さは各キャラクター 2〜4 ダンジョン。
- **王様の城（人間の承認）は、人間が決めるべき所だけ。** あがりの手前には必ず1つ。
- **国境（章）を越えたら、新しい大陸の最初に町を置く。** 前の章のあがり（突破したゲート）は、そのまま新しい大陸の最初の町になる（セーブポイント。Git でセーブする冒険ではコミットもされる）。
- **作戦はルールを変えない。** 人間は出撃のたびに作戦（いのちだいじに／バッチリがんばれ／ガンガンいこうぜ）を選べる。町の間隔が、ガンガンいこうぜで1回に進む長さになる。

### 8. 書いて、確かめて、始める

```sh
gridhub validate quests/<名前>.map.json     # 地図の検査
# 各道の最初の1〜2マスぶんの判定（tests/e2e/…）を書く。霧の先は後で書いてよい
gridhub new quests/<名前>.map.json           # 冒険の書をつくる（存在する判定ファイルは自動で封印）
gridhub serve                               # 盤面を開く
```

判定はマスに着く前に書けばよい（**遅延封印**）。未封印のマスは判定できないので、キャラクターが来る前に `gridhub seal <マス>`。

## キャラクターの起こし方（各エージェントへの最初の指示）

```
あなたは「<名前>」（ID: <id>）。GridHub の盤上のキャラクターです。
まず `gridhub brief <id>` を読み、現在のダンジョンだけを実装してください。
- 1マスずつ: いちばん手前の落ちているテストだけを通し、`gridhub step <id>` で確かめる（何度でも・罰なし）
- 縄張り: <territory> の外は編集しない
- 判定ファイル（tests/ など封印されたもの）は編集しない
- 全部のテストが通ったら `gridhub check <id>` で宣言判定（一発勝負）
- 終わる前に `gridhub note <id> "次の自分への申し送り"`
- ゲートで待機になったら、そこで止まって報告する
```

コンテキストが尽きたら、新しいセッションで同じ指示を出せば再開できる（指令書と日誌がセーブデータから復元する）。これが**伝承**: 出撃1回が1代で、次の代は先代の技と日誌を受け継ぐ。

### エージェントの箱（サンドボックス）を確かめる

判定が手元にサーバーを立てる（テストの中で `127.0.0.1` で listen する。偽の API・盤面の窓口など）なら、エージェントの箱の中でもそれができるかを出撃の前に確かめる。
Codex の `-s workspace-write` の箱は、既定でソケットを閉じていて、**`127.0.0.1` での listen まで** `EPERM` で止める。素振りも宣言判定も通らない（キャラクターのせいではないのにレベルが下がる）。
そのときは、箱のソケットを開けて出撃させる（CONTRACTS §30・§32）:

```sh
gridhub party --dry-run --agent codex --allow-listen             # 起動するコマンドを先に見る
gridhub party --agent codex --allow-listen --only engine,server  # その出撃だけ開ける
```

- **ゲームはローカルのまま**。インターネットが要るわけではない。開けるのは、判定が手元でサーバーを立てるときだけ。既定は閉じたまま。
- **注意**: 開けるのに使う Codex の設定（`sandbox_workspace_write.network_access`）は、localhost だけを許すことができない。開けると、その出撃中のエージェントは**インターネットにも出られる**。開けている出撃では、最初に「箱のソケット:」の知らせが出る。
- codex にだけ効く（codex のコマンドの `-s workspace-write` の後ろに `-c sandbox_workspace_write.network_access=true` が入る）。claude と `cmd:` のコマンドは変わらない。

いつも開けるなら `.masume/party.json` に `"allow_listen": true` を書く（盤面の「出撃させる」もこれに従う）。その回だけ閉じるなら `--no-allow-listen`。
願いから始めるときは `gridhub quest "<願い>" --gm codex --allow-listen` で GM の箱も開けられ（GM が判定を素振りするときも手元でサーバーを立てられる）、生まれた冒険の `party.json` にも `"allow_listen": true` が書かれる。`gridhub init --agent codex --allow-listen` でも書ける。

GridHub（旧名マスメ）自身の第4章では、伝令（窓口のサーバー）と地図職人（偽物の Linear・Jira を立てる判定）がこれにあたった。まだ選択肢が無かったので、`MASUME_AGENT_OVERRIDE` でアダプタごと差し替えた。
第5章でそれを選択肢にし、第6章で名前を `--network` から `--allow-listen` に改めた（「ローカルのゲームなのに、なぜネットワーク？」と誤解されたため）。

## 例: 「ことづけのようなアプリを作りたい」

> 電話の用件を AI が聞き取り、メールで届ける。申込→支払い→番号提供→受付開始。

```
ふりだし
 門番(番号と通話)   ■KTZ-1 ■KTZ-2 ─┐
 聞き手(AI受付)     ■KTZ-3 ■KTZ-4 ─┤★KTZ-G1 通話から用件が取れる ─ ■KTZ-5 ─┐
 書記(メール)       ■KTZ-6 ■KTZ-7 ───────────────────────────────┤★KTZ-G2 用件がメールで届く ─┐
 両替商(申込と支払い) ■KTZ-8 ■KTZ-9 ■KTZ-10 ───────────────────────┐                              │
 勇者(人間)         ■KTZ-11(ハンコ) ■KTZ-12(ハンコ) ─────────────┴★KTZ-G3 申し込んで使い始められる ┴★あがり
```

## チェックリスト

- [ ] あがりの判定が、ユーザーにとっての「完成」を1場面で確かめている
- [ ] どの task にも E2E の判定がある（人間のマスはハンコ）
- [ ] どの `cmd` の task にも `check.cases`（2〜6件）があり、判定ファイルのテストの名前と同じ
- [ ] `node --test` の判定は `node --test --test-reporter=spec <file>` で走らせる。パイプの先では既定が TAP になり、TAP はテストの名前の `#` を `\#` にするので、`cases` の名前と結びつかない。テストの名前には「空白のすぐ後の `#`」を書かない（` # SKIP` などの指示として、そこから後ろが切られる）。GridHub 自身の第11章で、B13 の名前（`見開き: #page-prev`）がこれに当たった
- [ ] 新しい冒険は `quest.save: "git"`、どのキャラクターにも重ならない `territory` がある
- [ ] すべての道が goal で終わる
- [ ] モジュールが初めてつながる所にゲートがある
- [ ] 縄張りが重なっていない
- [ ] 本物の外部サービス・本番の鍵に触る判定がない（人間のマスに分けた）
- [ ] 判定が手元にサーバーを立てるなら、Codex の出撃は箱のソケットを開けた（`gridhub party --allow-listen` か `party.json` の `"allow_listen": true`。その出撃中はインターネットにも出られることを承知のうえで）
- [ ] `gridhub validate` が通る
- [ ] 日誌・PR・Linear のコメントで「その時点」を指すときは、記録の番号と Git のコミットで書いた（`記録: seq 42 / Git: commit a1b2c3d`。`gridhub status` の最後の行）。戻るときは `gridhub load <seq>`、改ざんを見つけるのは `gridhub verify`
- [ ] ボス戦（ゲート）の前に、GM 自身がゲートの判定を素振りした（判定のバグで仲間を全滅させない）
- [ ] 判定の中で `node --test` を入れ子に呼ぶなら、環境変数 `NODE_TEST_CONTEXT` を外している（受け継ぐと何も走らずに通ってしまう）
- [ ] 章を足して新しいあがりを置いたら、`package.json` の `test:goal` を新しいあがりの判定に向け直した。あがりの判定（前の章までを全部まとめて走らせるもの）は `npm test` に入れない（何重にも同時に走って重くなり、ブラウザの判定が時間切れになる）
- [ ] 判定は、エージェントの箱（サンドボックス）の中でも走る。`ps` などは箱で禁止されることがある（Codex の `-s workspace-write` では `spawnSync ps EPERM`）。サーバーが残っていないかは、プロセスの一覧ではなく、ポートにつながるかで確かめる。マスメ自身の第8章で、GM の判定が `ps` を使っていて地図職人が素振りできず、GM が直して封印し直した
- [ ] 盤面の動き（アニメーション）を判定するなら、ページの用意ができた直後に一度だけ数えない。演出は待ち時間のあとで始まることがあるので、数秒のうちに始まるのを待つ。「動きを減らす」設定は `tests/helpers4.mjs` の `openBrowserWith({ media })` で真似できる。マスメ自身の第9章で、GM の B9 がすぐに数えていて、正しい盤面でも0件になった
- [ ] ゲートの素振りは**ボス戦と同じ環境**で走らせた。エンジンは判定に `MASUME_ROOT` `MASUME_CHARACTER` `MASUME_NODE` を渡す（例: `MASUME_ROOT=$PWD node --test tests/e2e/GOAL.test.mjs`）。判定の中で別の冒険の判定を走らせるなら、`MASUME_*` を外してその冒険のルートを渡す

## GM も間違える

判定は GM が書くので、判定そのものが間違っていることもある。そのときは:

1. 判定ファイルを直す（GM の縄張り）
2. `gridhub seal <マス>` で封印し直す（冒険の書に `sealed` として残る）
3. `gridhub note` で何を直したかを書く

キャラクターが素振りで「判定のほうがおかしい」と気づいたら、宣言せずに（ゲートなら `--no-boss` で）報告するのが正しい動き。
マスメ自身の冒険の書には、書記が G2 の判定の不備を素振りで見つけ、GM が直して再封印した記録が残っている。

GM のミスでボス戦に負けて全滅させてしまったら、キャラクターの主張が正しかったことを確かめたうえで、`gridhub load <ボス戦の前のseq>` で戻してよい（ロードしたこと自体が冒険の書に残る）。
マスメ自身の第2章では、GOAL2 の判定がボス戦の中の `MASUME_ROOT` を受け継いで負けた（seq 100）。GM が裁定を日誌に書き、seq 99 をロードし、判定を直して封印し直してから勝った。
