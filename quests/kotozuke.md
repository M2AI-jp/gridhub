# ことづけ — 電話の用件をメールで届ける地図

この説明書と [kotozuke.map.json](kotozuke.map.json) は、マスメの地図職人 `gmkit` が、M1「ことづけの地図を描く」で一度だけGM役を担当して作る開発計画である。ことづけの利用者は、電話で用件を伝える発信者と、その用件をメールで受け取る契約者である。運営は申込、入金照合、電話番号の提供を担当する。

今回作る成果物は、この地図と説明書の2ファイルである。地図に登場するアプリ、判定ファイル、本番設定は今後ことづけのリポジトリに用意するものであり、M1で実装・実行済みという意味ではない。

正本は [AGENTS.md](../AGENTS.md)、[ルールブック](../docs/RULEBOOK.md)、[GMガイド](../docs/GM_GUIDE.md)、[契約書 §2・§10](../docs/CONTRACTS.md) と、今回のユーザー指令書である。地図の形式、進行と封印、職業・色はこれらの文書に従う。サービスに関する情報の確認範囲は、ユーザーが提示した要約までであり、実在サービスのソースコード、本番設定、外部サービスの最新仕様は確認していない。

## ヒアリング（想定問答）

以下の3問はGMガイドのヒアリングに相当する。回答はユーザーの要約から構成した想定であり、実際に質問して回答を得た記録ではない。

1. **誰が、どの入口から使うか。**  
   想定回答：発信者は契約者の電話番号に電話し、AIに用件を預ける。契約者はメールで用件を読む。新しい契約者は紹介LPからGoogleフォームで申し込み、運営がGmailで支払いを案内し、PayPalの入金を照合して番号を提供する。
2. **どの外部サービスを使い、本番の準備を誰が行うか。**  
   想定回答：Twilioが電話番号と着信を扱い、OpenAI RealtimeがSIP経由で音声を受ける。Cloudflare Workers / Durable Objects（SQLite）が処理と保存を担う。人間が本番アカウントと鍵、PayPal接続、利用規約、番号購入、実電話試験を担当する。
3. **どの場面が動けば完成とするか。**  
   想定回答：申込と入金照合を終えた契約者に番号が届き、その番号に電話して話した用件がメールで届く。AIは名前・用件の不足だけをまとめて最大1回尋ね、営業電話も受領する。標準契約の3分・支払月50件を守り、メール送信成功後にアプリ内の会話本文が削除される。

## あがり

**LPから申し込んだ契約者が支払いと運営の入金照合を経て番号を受け取り、その番号に届いた電話の用件が「誰から→日時/期限→依頼→会話→連絡先」の順のメールで届き、送信成功後にアプリ内の会話本文が消えている。**

この一場面を最後の結合ゲート `KTZ-GOAL` のE2Eで確認する。E2Eとは、利用者や運営が使う入口からアプリを動かし、出力や保存結果までを確認する判定である。自動判定は電話、AI、フォーム、メール、決済をローカルの代替サービスに接続する。実際の音声認識品質、本番での到着時間、実電話の接続可否は、この判定の成功だけでは確認できない。

全キャラクターの道は `KTZ-GOAL` で終わる。勇者はその直前の `KTZ-H4` で本番の実電話試験と公開承認を行う。ハンコは人間本人の確認であり、フェイクの成功結果から自動で押してよいものではない。

## キャラクター

各キャラクターは一つの担当モジュールを持つ。ディレクトリは今後のことづけリポジトリ内の縄張りであり、このM1でそれらのファイルを作る指示ではない。各エージェントのtaskは2〜4マスで、1マスを1回の作業に収める想定で分けた。人間の作業時間や外部審査の所要時間は見積もっていない。

| ID / 名前 | 種別・職業・色 | 担当と縄張り | task |
| --- | --- | --- | --- |
| `phone` / 門番 | agent / warrior / blue | 番号に対応する着信処理、SIP接続、通話の分離と時間制限。`src/phone/**` | `KTZ-1`〜`KTZ-4` |
| `listener` / 聞き手 | agent / mage / purple | AI受付、追加質問、用件の整理。`src/listener/**` | `KTZ-5`〜`KTZ-7` |
| `mailer` / 伝令 | agent / herald / green | 用件メール、配送状態、本文削除。`src/mailer/**` | `KTZ-8`〜`KTZ-11` |
| `billing` / 両替商 | agent / merchant / orange | 申込、入金照合、番号割当て、開始案内、月枠。`src/billing/**` | `KTZ-12`〜`KTZ-15` |
| `lp` / 絵師 | agent / painter / pink | 紹介LPと申込導線。`web/lp/**` | `KTZ-16`、`KTZ-17` |
| `operator` / 勇者 | human / hero / yellow | 本番の準備・規約・実電話試験・公開承認。秘密を含まない運用記録は `ops/**` | `KTZ-H1`〜`KTZ-H4` |

色と縄張りは重ならない。地図の各 `detail` に作業主体、操作対象、合格条件を記し、各 `check` に判定コマンドまたはハンコの担当者を記した。

### データと共有部分の責任

以下はことづけ側の実装に向けた分担案である。実装用の型、HTTP契約、認証方法は、そのリポジトリのGMが契約として確定する。

| 情報・操作 | 正本を持つ担当と、他担当との境界 |
| --- | --- |
| 契約、入金照合、番号の割当て、期間と件数 | 両替商が正本を持つ。門番は契約の参照と月枠確保をこの担当へ要求し、独自の月次カウンターを持たない。番号そのものの購入は勇者が行う。 |
| 通話の接続と時刻 | 門番が契約ID・通話ID・受付時刻を確定し、聞き手と伝令へ渡す。重複した着信は同じ通話として扱う。 |
| 会話の整理 | 聞き手が用件を作り、伝令への保存が確認できたら手元の本文を消す。門番と聞き手は会話を永続保存しない。 |
| 配送待ちの本文 | 伝令が未送信本文と配送状態の正本を持つ。成功後は本文を消し、本文を含まない配送状態だけで再送・重複を管理する。 |
| LP、共有の規約 | 絵師は紹介と導線を担当する。規約の内容は勇者が承認し、LPはGMが用意した承認済みの公開先を参照する。 |
| モジュールの結線と共通設定 | ことづけ側のGMが共有の型、ルーティング、ローカル実行器、環境設定、`tests/**`、`package.json`などを管理する。エージェントは縄張り外を編集せず、結合ゲートに必要な変更をGMへ依頼する。 |

## 地図スケッチ

ASCIIの各行は1人の道を表す。番号の前の `KTZ-` は省略した。同じ `[G1]` などは同一のゲートであり、その行の全員が到着してから判定する。丸括弧は宿屋、`H1`〜`H4` は人間のハンコである。地図JSONの `path` が正式な順序である。

```text
START
  phone    : 1--2----------[G1]--3--------[G2]--[G3]--4---[G4]------[GOAL]
  listener : 5--6----------[G1]--7--------[G2]-------------[G4]------[GOAL]
  mailer   : 8--9--(C1)--10--11-----------[G2]-------------[G4]------[GOAL]
  billing  : 12--13--(C2)--14-------------------[G3]--15--[G4]------[GOAL]
  lp       : 16--17----------------------------[G3]----------------[GOAL]
  operator : H1--H2----------------------------[G3]--H3--[G4]--H4--[GOAL]
```

ゲート間の依存順序は `G1 → G2 → G3 → G4 → GOAL` である。各担当は合流前の作業を並行して進められる。例えば伝令は門番と聞き手がG1を進める間に配送を用意する。ゲート突破後は各人が自分の道の次のマスへ進む。

## ゲート

ゲートのメンバーはJSONの `path` から決まり、別のメンバー一覧を地図に追加しない。次の表はその説明である。各ゲートのE2Eでは、参加する実装モジュールを実際につなぎ、外部事業者の部分だけをフェイクにする。

| ゲート | メンバー | 初めてつなぐ境界と合格条件 |
| --- | --- | --- |
| `KTZ-G1` 電話から用件を受け取る | 門番・聞き手 | 電話入口からAI受付へつなぐ。会話から用件を取得し、追加質問の上限、営業電話の受領、通話の分離、3分の終話を確認する。 |
| `KTZ-G2` 用件を届けて本文を消す | 門番・聞き手・伝令 | 通話の受付結果を配送へつなぐ。正しい契約者に指定の項目順で届き、成功後は各担当の保存領域に本文が残らないことを確認する。失敗後の再送と重複も通す。 |
| `KTZ-G3` 申し込んで電話を使い始める | 門番・両替商・絵師・勇者 | LPと申込、契約台帳と番号に対応する電話入口をつなぐ。申込→支払い案内→フェイク決済→運営照合→番号提供→開始案内→着信を通す。ここではG2で確認済みの有効契約の通話経路を使い、実台帳への月枠確保はG4で結合する。 |
| `KTZ-G4` 同時受付と月枠を両立する | 門番・聞き手・伝令・両替商・勇者 | 門番の受付判断と両替商の永続カウンターを結合する。残り1件に2通話が来ても1件だけがAI受付からメール配送へ進み、別契約の電話は独立して進む。再起動、重複、期間更新でも月枠を守る。 |
| `KTZ-GOAL` あがり | 全6人 | 新しい架空の契約者で、LPから申込・入金照合・番号取得・電話・メール・本文削除までを通す。途中で確認した制限と失敗時の挙動も再確認する。勇者は直前にH4を完了している必要がある。 |

G3に人間が参加するため、アカウントの準備と運用条件の確認を終えずに次へ進むことはできない。G4も勇者を待ち、本番の番号・接続の準備後にH4の実電話試験へ進む。ただし、G3・G4のコマンド自体は本番設定や実アカウントを参照しない。

ゲートの判定が原因を特定できた場合は、例えば `MASUME_BLAME: mailer`、複数なら `MASUME_BLAME: phone,billing` と出す。出せるIDはそのゲートのメンバーだけである。原因を特定できないときは行を出さず、ルールどおり全員が差し戻される。テストの失敗を人間の本番作業の失敗と推測してはならない。

## 人間の道とハンコ

| マス | 実施の順序と、人間本人が確認する内容 |
| --- | --- |
| `KTZ-H1` | 最初にTwilio・PayPal・Googleの本番アカウントと鍵を用意し、OpenAI・Cloudflareの権限も確認する。鍵を秘密保管先に置き、地図やテストに書かない。 |
| `KTZ-H2` | 規約、料金、支払期間、件数の定義、未送信本文の保持期限、削除範囲を承認する。前提に変更が必要なら、GMの改訂を経てからG3へ進む。 |
| `KTZ-H3` | G3の利用開始フローを確認した後、実番号を購入し、PayPal本番接続、Googleフォーム・Gmail、電話の接続先を設定する。費用と本番設定の変更はこの人間の作業に属する。 |
| `KTZ-H4` | G4突破後、同意を得た試験用契約者と実電話を使い、用件、追加質問、時間制限、同時受付、メール到着、本文削除を確認する。秘密や会話を含まない記録を残し、公開を承認してからGOALへ進む。 |

いずれも `check.kind: "stamp"`、`by: "operator"` のtaskである。ゲート自体はコマンド判定とし、ハンコに置き換えない。M1の地図職人は、これらの本番作業を実施したり人間に代わって承認したりしない。

## 宿屋と戻り先

伝令の4つのtaskの途中に `KTZ-C1`、両替商の道の入金照合後に `KTZ-C2` を置く。宿屋は判定を持たず、到着すると自動でセーブされる。他の長い道は途中の結合ゲートがセーブポイントになり、ゲート間に4つ以上のtaskは続かない。

taskの戻り先は原則 `@camp` とする。追加質問の調整 `KTZ-6`、番号の割当て `KTZ-14`、人間のtaskは `@here` とした。強い依存がある箇所は、通話制御を番号受付へ (`KTZ-2 → KTZ-1`)、メール送信を整形へ (`KTZ-9 → KTZ-8`)、本文削除を再送処理へ (`KTZ-11 → KTZ-10`)、入金照合を申込へ (`KTZ-13 → KTZ-12`)、LP導線を紹介ページへ (`KTZ-17 → KTZ-16`) 戻す。

これらは全て同じ道の前のマスである。実際の巻き戻しはルールブックに従い、直近の宿屋・突破済みゲートより前へは戻らない。宿屋で累積判定の区間が切れても、後続ゲートでは区間をまたぐ利用者の流れを再確認する。

## 判定コマンドと封印

17のエージェントtaskと5つのゲートには、ことづけリポジトリのルートから実行する、次の形式のコマンドを記した。

```sh
node --test tests/e2e/KTZ-3.test.mjs
node --test tests/e2e/KTZ-GOAL.test.mjs
```

各 `check.seal` には、そのマスの `tests/e2e/<マスID>.test.mjs` と、共通の `tests/helpers.mjs`、固定入力の `tests/fixtures/kotozuke.json` を指定した。ここでいう判定ファイルは将来のことづけリポジトリに置くものであり、マスメ側に同名のファイルがあっても代用しない。M1ではこれらのファイルを作成しない。

ことづけ側のGMは、判定と共通道具を作り、冒険の開始時または各マスへの到着前に封印する。判定に追加の補助ファイルを使う場合は、凍結前にそのファイルも `seal` へ追加する。ファイルがない判定は未封印のままであり、仮の成功や固定の出力で通過させない。

判定を実装するGMは、次の条件を守る。

1. E2EはアプリのHTTP・CLI・静的ページなど外部から使える入口を通し、フェイク受信箱、操作への応答、生成メール、ローカル保存物で結果を確認する。内部関数の結果だけで合格にしない。
2. Twilio、Realtime/SIP、Googleフォーム、Gmail、用件メール、PayPalにはローカルのフェイクを使う。PayPalのサンドボックスに相当する成功・失敗も固定データで再現し、外部のサンドボックスへ接続する資格情報は要求しない。
3. 判定の子プロセスへ本番の鍵を渡さず、接続先をループバックに限定する。想定外の外向き通信は失敗にする。実際の電話、メール、決済、番号購入を発生させない。
4. フェイクに置き換えるのは外部サービスと未結合の相手境界である。ゲートでは参加モジュールの実装をつなぎ、入力をそのまま期待値として返すだけの代用品でアプリの判定を済ませない。
5. 判定ごとに一時ディレクトリと独立した保存領域・空きポートを用意する。時計、期間、通話ID、架空の金額、会話イベントを固定し、後処理でサーバー・DB・一時領域を閉じて片付ける。累積判定でも繰り返し実行できることを確認する。
6. 件数や配送状態の永続化は、同じ判定内でアプリを再起動して確認する。SQLiteを使うローカル実行環境をことづけ側のGMが準備し、単なるメモリ上のカウンターで永続化の合格を代用しない。
7. 会話、メールアドレス、電話番号、鍵は架空の入力を使う。実在の契約者の会話を判定やログに取り込まない。

固定のRealtimeイベントによる判定は、受付の制御やイベント処理の再現性を確かめるためのものになる。音声品質と実際の接続はH4で人間が確認する。

## 開始前にGMが用意するもの

ことづけ側のGMは、前提と共有の実装契約、ローカル実行環境、最初の1〜2マス分のE2Eを準備する。残りのE2Eは該当マスへの到着前に用意して封印する。新しい外部パッケージや共有ファイルの変更を各キャラクターが独断で行わない。

GMガイドに沿う開始手順は、地図の検査、判定の準備、冒険の書の作成、盤面の起動の順である。

```sh
node bin/masume.js validate quests/kotozuke.map.json
node bin/masume.js new quests/kotozuke.map.json
node bin/masume.js serve
```

この手順は、マスメのCLIとことづけの判定を使える環境をGMが整えてから実施する。`new` と `serve` はM1の実施範囲に含めない。今回の地図作成を判定するコマンドは、マスメ側の `node --test tests/e2e/M1.test.mjs` である。この判定が確認するのは成果物の存在、地図の構造、要件の記述であり、ことづけの機能が完成したことではない。地図検査CLIの利用可否とM1判定の実行結果は、地図職人の報告書に記す。
